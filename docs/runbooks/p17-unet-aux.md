# P17 — U-Net 영상 브랜치 + 코로나홀 보조 감독

P17 은 P3 를 베이스로 하되 **피처를 손으로 만들지 않는다.** 코로나홀이 태양풍 속도에
영향을 준다는 사실만 남기고, 그 코로나홀을 *어떤 숫자로 접을지* 는 U-Net 이 학습으로
정한다. 탄도 정렬 피처는 완전히 제거했다.

| | P3 | P17 |
|---|---|---|
| 코로나홀 | 3×5 격자 면적 15개 실수를 **입력**으로 | 같은 임계값 마스크를 **라벨**로 (U-Net 디코더가 맞힌다) |
| 영상 인코더 | Inception3D (기본 꺼짐) | **U-Net** (항상 켬) |
| 영상 시계열 | LSTM | **GRU** (바람 브랜치와 동일) |
| 탄도 정렬 | horizon별 3속도 역산 | **제거** |
| 나머지 | 결측 처리 · 잔차 학습 · 공식 지표 · 증강 | P3 와 동일 |

## 1. 코로나홀이 들어가는 경로

```
프레임 --U-Net 인코더--> bottleneck --디코더--> CH 확률맵  <--(가중 BCE)-- P3 임계값 마스크
                            |                       |
                            +--- CH 확률로 가중 평균 --+--> 프레임 임베딩 --GRU--> 잔차 12개
```

임계값 규칙(193·211 두 채널 모두에서 원반 중앙값의 45% 미만)은 P3 와 글자 그대로
같다. **다른 것은 쓰는 자리다.** 모델에 먹이는 대신 정답으로 주고, 그 영역에서 무엇을
읽을지는 인코더가 정한다. 회귀로 흘러가는 값은 격자 면적이 아니라
`bottleneck 전역평균 ‖ CH확률 가중평균` 두 벡터다.

bottleneck 에는 학습되는 위치 임베딩을 더한다. 원반 위 어디가 중요한지를 손으로
정하지 않기 위한 것이다 — P10 이 중앙자오선 밴드로 좁혔다가 2.98 잃은 것에 대한 대응.

## 2. 준비물

캐시도 필요 없다. 노트북 하나만 올리면 된다.

| 캐시 | 만드는 곳 | 재사용 |

| `work/cache/ch_*_3x5_0.45_128.npy` | 노트북 셀 3 (P3 와 동일) | P3 캐시 재사용 |
| `work/cache/median_*_128_0.95.npy` | 노트북 셀 4 (P17 신규) | 이미지당 원반 중앙값 2개. 몇 초면 만든다 |

## 3. 실행

[code_p17.ipynb](../../experiments/p17-unet-aux-supervision/code_p17.ipynb)를 위에서부터 실행한다. 설정 셀에서 건드리는 값은 다음 셋뿐이다.

```python
USE_UNET = True        # P17 의 본체
USE_CH_AUX = True      # 코로나홀 보조 감독
USE_CH_GRID = False    # P3 격자 브랜치 (대조용)
```

마지막 validation 셀의 `P17 OFFICIAL_VALIDATION_RMSE` 가 비교 점수다. 비교할 때
`SEED`, `EPOCHS`, early-stopping 설정은 고정한다.

### 비용 (측정값, RTX 4060 8GB 기준)

| batch | peak VRAM | 처리량 |
|---:|---:|---:|
| 8 | 1.20 GiB | 83 samples/s |
| 16 | 2.35 GiB | 86 samples/s |
| 32 | 4.66 GiB | 86 samples/s |

`BATCH_SIZE = 32` 이 기본값이다. OOM 이면 16 → 8 로 내린다 (처리량은 거의 안 변한다).
서버 GPU 가 더 크면 `UNET_BASE = 32` 로 올려 볼 수 있다.

**너무 느리면 `FRAME_STRIDE = 2`.** 20 프레임을 10 으로 줄여 U-Net 비용이 정확히
절반이 된다. 6h 간격을 12h 로 벌리는 셈인데, 코로나홀은 하루에 13° 남짓 돌 뿐이라
잃는 정보가 크지 않다. 다만 **조합 비교 중에는 고정할 것.**

## 4. 권장 실행 순서

한 번에 하나씩만 바꾼다.

| # | 설정 | 답하는 질문 |
|---|---|---|
| 1 | 기본값 그대로 | P17 이 persistence 와 P3(64.203) 대비 어디에 있나 |
| 2 | `AUX_CH_WEIGHT = 0` | **보조 감독이 값을 하는가.** 같은 U-Net·같은 GRU, 감독만 뺀 대조군 |
| 3 | `USE_UNET = False` | 바람 브랜치만의 바닥. 영상이 실제로 기여하는 폭 |
| 4 | `USE_CH_GRID = True` | 학습된 CH 표현 + 손으로 만든 격자를 함께 넣으면 더 나은가 |

2번이 제일 중요하다. **1번과 2번이 3 km/s 안에서 비슷하면 U-Net 은 그냥 큰 모델일
뿐이고, 코로나홀 감독은 일하지 않는 것이다.** 그때는 P17 을 제출 후보로 올리지 말 것.

## 5. 읽을 때 주의

* **영상 브랜치는 이 데이터에서 네 번 실패했다.** P2(과적합) → P3(끔) → P6(Public 패)
  → P10(대조군에 3종 전패). 고유 이미지 10,139장이 실질 자전 135회분뿐인 것이 원인으로
  지목됐다 (`CODE_REPORT.md` §5.2). P17 의 보조 감독은 정확히 그 실패를 겨눈
  대응책이지만 **검증된 처방은 아니다.** 4절의 2번 대조군이 유일한 판정 근거다.
* **val 계측 노이즈 바닥은 약 3 km/s 다.** 1~2 km/s 차이는 순위 근거가 못 된다.
  게다가 리더보드는 계단 하나가 0.153 km/s 다 (§5.1). 로컬 val 로 못 가르는 구간이다.
* **학습 곡선의 오른쪽 패널(CH 보조 BCE)을 먼저 본다.** 이 값이 안 내려가면 감독이
  아예 안 걸린 것이고, 그 상태의 RMSE 비교는 의미가 없다.
* **validation 셀 마지막 그림**에서 `임계값 라벨` 과 `U-Net 예측 CH 확률` 이 눈으로
  비슷해야 한다. 예측이 전면 0.5 근처면 아직 학습이 안 된 것이다.
* `AUX_POS_WEIGHT` 는 train CH 양성 비율에서 자동으로 정해지고 [1, 10] 로 잘린다.
  10 에 붙어 찍히면 CH 가 매우 희소하다는 뜻이다.
