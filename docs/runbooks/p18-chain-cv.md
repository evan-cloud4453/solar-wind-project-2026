# P18 — P3 + 사슬 CV 계측기

P18 은 **새 모델이 아니다.** P3(Public 58.8028, 현재 최고 제출)의 모델·피처·손실·증강을
글자 단위로 그대로 두고, *무엇을 보고 epoch 을 고르는가* 만 바꾼다.

| | P3 | P18 |
|---|---|---|
| epoch·체크포인트 선택 | official validation 최저점 (60 중 1회 선택) | **train 사슬 CV 평활 곡선의 최저점** |
| validation | early stopping · 체크포인트 선택에 사용 | **마지막에 1회 읽기만** |
| LR 스케줄 | `ReduceLROnPlateau` (val 에 의존) | **`CosineAnnealingLR`** (데이터 비의존) |
| 모델·피처·손실·증강·전처리 | — | **P3 와 동일** |

노트북은 P3 원본을 다시 타이핑하지 않는다. [build_p18_notebook.py](../../src/builders/build_p18_notebook.py)
가 `Trial/P3/code_p3.ipynb` 를 읽어 **세 군데만 패치**한다. 그래서 "모델이 P3 와 같다"는
주장이 검증 가능하다 — 나머지 셀은 원본 객체 그대로다.

## 1. 왜 계측기부터인가

P3 의 val 64.203 은 **60 epoch 중 최저값**이다. 그 val 은 1,199 샘플 = 자전 11.2회전뿐이고,
그 위에서 60번 고르면 최저값은 실력이 아니라 운을 상당 부분 담는다. 반면 train 은 28개
사슬 = **자전 93회전**이다. 통계적 힘이 8배 이상 차이 난다.

무작위 행 분할이 왜 안 되는지도 수치로 박아 둔다 — 측정값이다.

| 분할 | eval 프레임 중 train 에도 등장하는 비율 |
|---|---|
| 무작위 행 분할 (5:1) | **99.8%** |
| 사슬 통째 배정 (P18) | **0%** |

샘플이 6h stride 슬라이딩 윈도우라 이웃 창이 입력의 19/20 을 공유하기 때문이다.
사슬을 통째로 배정하면 프레임 공유가 구조적으로 0이라 embargo 도 필요 없다.

## 2. 준비물

**추가 추출이 없다.** P3 캐시를 그대로 쓴다.

| 캐시 | 재사용 |
|---|---|
| `work/cache/128px/{split}_images.npy` | P3 것 그대로 |
| `work/cache/ch_{split}_3x5_0.45_128.npy` | P3 것 그대로 |

사슬 복원은 노트북 안에 들어 있다(셀 5). `timeline.parquet` 같은 외부 파일에 의존하지
않는다 — 제출 노트북이 자기 완결이어야 하기 때문이다.
[build_timeline.py](../../src/analysis/build_timeline.py) / [chain_cv.py](../../src/analysis/chain_cv.py) 는 같은 규약의
**오프라인 분석용**이고, 노트북 실행에는 필요 없다.

## 3. 실행

```bash
python build_p18_notebook.py
```

그다음 [code_p18.ipynb](../../experiments/p18-chain-cv/code_p18.ipynb) 를 위에서부터 실행한다. 건드릴 값은 셀 3 의 노브다.

```python
P18_N_FOLDS = 5        # 사슬 grouped CV 폴드 수
P18_N_REPEATS = 3      # 배정을 다시 뽑는 횟수 (사슬 길이가 33~980 로 불균등)
P18_CV_SEEDS = (777,)  # (777, 778, 779) 로 늘리면 비용도 3배
P18_STRIDE = 0         # rung 0 은 반드시 0. 다음 칸에서 9 로 올린다
```

기본값이면 학습 15회(폴드 5 × 반복 3 × 시드 1)다. 노트북이 폴드마다 경과·남은 예상
시간을 찍으므로 첫 줄에서 총 비용을 알 수 있다. P3 는 `USE_CNN=False` 라 한 epoch 이
가볍다.

## 4. 읽는 법

마지막 두 숫자를 나란히 본다.

```
[CV] 공식 RMSE   = xx.xxx +- x.xxx km/s     <- 자전 93회전, 15회 평균
공식 RMSE (mean of horizon RMSE) : xx.xxx   <- 자전 11.2회전, 1회
```

- **두 값이 크게 어긋나면** 그 자체가 결과다. §1.5 의 "val 도 CV 도 P9/P10 순위를 못 맞혔다"
  는 문제에 대해, 이번엔 어느 쪽이 얼마나 흔들리는지를 표준오차와 함께 보게 된다.
- **P18 을 제출할지는 CV 로 정하지 않는다.** P3 대비 개선을 주장하려면 Public 이 필요하다.
  P18 의 역할은 다음 칸(아래)을 **제출 없이 고를 수 있게** 만드는 것이다.
- `cv_curves.npy` 에 (15, 60, 12) 곡선 전체가 남는다. horizon별·폴드별 재분석이 가능하다.

## 5. 주의 — 남겨 둔 근사

**정규화 통계는 train 전체에서 뽑는다.** `CH_MEAN/STD`, `WIND_MEAN/STD`,
`RESIDUAL_MEAN/STD`, `CLIP_LOW/HIGH` 가 폴드 평가 구간까지 포함해 계산된다.
P9 는 `fit_stats(train_rows)` 로 폴드마다 다시 뽑았다.

여기서 안 한 이유는 두 가지다. (1) 전역 스칼라라 80% 표본으로 다시 뽑아도 값이 거의
같다. (2) 무엇보다 **비교되는 두 설정에 같은 방향으로 걸리므로 대응비교는 영향받지
않는다.** 다만 **CV 절대값은 미세하게 낙관 편향**이다 — Public 과 직접 비교하지 말 것.

폴드마다 다시 뽑으려면 `ch_seq`·`ballistic` 배열을 폴드마다 재생성해야 해서 시간·메모리
비용이 붙는다. 필요해지면 그때 한 칸으로 따로 올린다.

## 부록 — P9 폴드 설계에서 나온 것

P18 을 만들며 [Trial/P9/code_p9.ipynb](../../experiments/p09-paired-cv/code_p9.ipynb) 의 폴드 전제를 실측했다.

```python
# P9 의 점검식
heads = [chain[0] for chain in TRAIN_CHAINS]
CHAIN_ORDER_IS_TIME = heads == sorted(heads)
```

사슬은 `for head in sorted(names - set(predecessor))` 로 만들어진다. 따라서 `heads` 는
**구성상 항상 정렬돼 있고**, 이 점검은 언제나 `True` 다. 경고가 뜰 수 없는 경고문이다.

파일명이 실제로 시간을 담는지 직접 재면:

| 측정 | 값 |
|---|---|
| 사슬 내부에서 파일명 id 가 증가하는 비율 | **49.7%** (시간 인코딩이면 100%, 무작위면 50%) |

파일명은 익명화되어 있고 **28개 사슬의 실제 시간 순서는 주어진 데이터로 복원 불가능**하다.
따라서 P9 의 `FOLD_MODE="block"` 은 "시간 연속 블록"이 아니라 무작위 그룹 분할이고,
`FOLD_MODE="forward"`(전진 검증)는 의미가 없다.

**누수 측면에서는 문제가 없다** — 사슬을 통째로 배정하는 한 윈도우 중첩은 0이다.
틀린 것은 동작이 아니라 *표방한 성질*이고, "test 는 미래 계절이므로 이 폴드가 일반화
격차를 잘 반영한다"는 P9 의 근거는 성립하지 않는다. P18 은 이 사실을 인정하고, 대신
**배정을 여러 번 다시 뽑아 평균낸다**(`P18_N_REPEATS`).
