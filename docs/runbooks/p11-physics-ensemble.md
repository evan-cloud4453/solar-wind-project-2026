## 0. 올릴 파일

대회 서버 작업 디렉터리(=`public_dataset/` 이 보이는 곳)에 둘 것.

| 파일 | 역할 | 제출물 |
|---|---|---|
| `code_p11.ipynb` | 학습·추론·제출물 생성 전부 | **예** (`submission/code.ipynb`) |

그 뒤에서 필요한 함수만 재정의한다. `work/cache/` 의 **P7/P9 캐시(`p7a`)가 그대로
재사용**되므로 CH 재추출은 하지 않는다.

## 1. t=0 — 추출부터 백그라운드로 던진다

노트북을 여는 것보다 **이게 먼저다.** 40~60분 걸리고, 그 동안 노트북 작업을 한다.

먼저 30장으로 스모크 테스트 (1분 안에 끝난다):

```bash
python p11_extract.py --limit 30 --workers 2
```

`형태 백엔드 cv2` 또는 `scipy` 가 찍히면 정상이다. `numpy` 가 찍히면 연결성분(형태
스칼라)이 안 나오고 θ_b 는 침식 근사가 된다 — 노트북이 알아서 그 열을 뺀다.

이상 없으면 전체를 백그라운드로:

```bash
nohup python p11_extract.py --workers 4 > extract.log 2>&1 &
```

```bash
tail -f extract.log
```

- **워커는 4개를 넘기지 말 것.** 운영진 공지 — 다중 프로세스로 VM 이 내려간 전례가 있다.
- 중간에 끊겨도 `.part.npz` 만 남고 본 파일은 손상되지 않는다. 다시 돌리면 된다.
- `train` → `validation` → `test` 순서다. `test` 가 마지막이라 중간에 끊겨도 앞은 남는다.
- 결과: `work/cache/p11a_{train,validation,test}.npz`

**추출이 없어도 노트북은 끝까지 돈다.** `p11a 캐시: 없음` 이 찍히고 [L3] 이 자동으로
꺼진 채 [L1]+[L2] 만으로 제출물이 나온다. S1·S2 는 추출을 기다릴 필요가 없다.

## 2. 노트북 — 바꾸는 것은 `STAGE` 한 줄뿐

`code_p11.ipynb` 를 열고 위에서부터 순서대로 실행한다. P11 설정 셀에 있는

```python
STAGE = "S1"                    # S1 -> S5 / S5M
```

이 한 줄만 제출할 때마다 바꾼다. 기하·물리·탄도창·수축·시드 수는 전부 `STAGE_TABLE` 이
정한다. **손으로 켜는 스위치는 없다.**

| STAGE | 멤버 | 추가되는 레버 | 추출 필요 |
|---|---:|---|---|
| `S1` | 6 | [L1] 앙상블만 (구 기하) — **제출됨 59.7332, 패 (§7)** | 아니오 |
| `S2` | 6 | + [L2] μ 보정 · 등각 경도 | 아니오 |
| `S3` | 9 | + [L3] θ_b · 형태 | **예** |
| `S4` | 9 | + [L4] 탄도창 확장 + [L5] 수축 | **예** |
| `S5` | 15 | 시드 5개로 확대 | **예** |
| `S5M` | 12 | S5 대안 — **구 기하와 새 기하를 같이 평균** | **예** |

멤버 하나가 1~2분이므로 S1 은 GPU 약 10분, S5 는 약 25분이다.
S4·S5 는 [L5] OOF 적합으로 폴드 수(5)만큼 학습이 더 붙는다 (+5~10분).

셀을 처음부터 다시 돌릴 필요는 없다. **P11 설정 셀부터** 아래로 다시 실행하면 된다.

## 3. 제출 사다리 — 5회를 계측기로 쓴다

| # | STAGE | 기대 | 결과가 나쁘면 |
|---|---|---|---|
| 1 | `S1` | 57.2~58.0 | **즉시 중단하고 P3 유지.** 앙상블이 안 먹으면 나머지도 안 먹는다 |
| 2 | `S2` | −0.3~1.0 | L2 폐기 → 다음은 `S1` 기하로 되돌린 조합 |
| 3 | `S3` | −0.5~2.0 | 물리 피처 폐기 → S4 를 `S2 + L4 + L5` 로 |
| 4 | `S4` | −0.3~1.0 | L4·L5 통째 폐기 (분리 측정 불가) |
| 5 | `S5` 또는 `S5M` | −0.1~0.4 | 멤버 수 확대분만 |

**정지 규칙.** 직전 최고보다 **+0.5 이상 악화**하면 그 레버는 버리고 직전 최고로 되돌린다.
Public 은 best score 를 표시하므로 나쁜 제출이 순위를 끌어내리지 않는다.

**추출이 60분을 넘기면** S3 을 `S2 + L4 + L5` 로 바꾸고 L3 을 S4 로 미룬다.
(그 조합은 `STAGE_TABLE["S4"]` 에서 `physics=False` 로 두면 나온다.)

`S5` 와 `S5M` 중에서는 — **멤버간 예측 불일치가 크게 나왔으면 `S5M`** 이다.
불일치가 클수록 서로 다른 기하를 섞는 평균의 이득이 크다. 그 값은 학습 셀이 찍어 준다
(`멤버간 test 예측 불일치 ... RMS km/s`).

1. **재현성 검증 셀**: `model.pth` 만 읽어 `submission.csv` 를 다시 만들고 RMS 차이를 잰다.

   `submission/code.ipynb` 로 복사한다.

## 6. 이 코드가 어디까지 검증됐나

대회 데이터 없이 **같은 레이아웃의 합성 소형 데이터셋**(96px, train 78 / val 21 / test 21
샘플)으로 전 경로를 실행해 확인했다.

검증된 것:

- `S1` `S2` `S3` `S4` `S5` `S5M` 여섯 단계 모두 **전 셀 통과**
- `model.pth` → 재추론 → `submission.csv` **재현 오차 0.000000**
- `p11_extract.py` 의 `area` 가 P9 `p7a` 캐시와 **최대 오차 0** (같은 알고리즘·같은 프레임 순서)
- 백엔드 3종(`cv2` / `scipy` / `numpy`) 모두 동작. `numpy` 일 때 상수가 되는 형태 스칼라는
  노트북이 자동으로 뺀다
- `p11a` 캐시가 없을 때 [L3] 자동 차단 후 정상 종료

검증되지 않은 것 (실데이터가 있어야 한다):

- **성능.** 합성 데이터의 RMSE 는 아무 의미가 없다
- GPU 실제 소요 시간 (위 추정치는 P9 의 step 수에서 환산한 것)
- 추출 실제 소요 시간

## 7. 🔴 S1 제출 결과 (2026-08-20 20:14) — 59.7332, P3 에 0.93 패

```
멤버 val : A0 66.608 / 67.653 / 66.982   F3 66.996 / 69.304 / 67.234
멤버 평균 67.463  ->  앙상블 65.622      멤버간 test 불일치 22.53 RMS
Public   59.7332   (P3 58.8028 / P9 59.2246 / N1 59.7313)
```

**계획의 정지 규칙이 발동한다: 최고 제출은 P3 (58.8028) 그대로다.**

### 앙상블은 작동했다. 멤버가 나빴다.

- 평균은 수학대로 먹혔다 — 멤버 평균 67.46 → 65.62 (**−1.84**).
- 다양성도 충분했다 — 멤버간 불일치 **22.53 RMS**. P3↔P9 의 25.93 과 비슷한 수준이다.
- 그런데 Public 은 59.73 이다. 관측된 불일치와 K=6 으로 역산하면 **멤버 하나가 단독으로
  약 61.5** 였다는 뜻이다. P9 단독(59.22)·P3 단독(58.80)보다 나쁘다.

### 원인 — `A0` 는 P3 가 아니다

`A0` 를 "P3 재현" 이라 불렀지만 재현된 것은 **피처/알고리즘 설정뿐**이고 **학습 레시피가
아니다.** 나머지는 전부 같다 (`BATCH_SIZE 64` · `lr 3e-4` · `weight_decay 1e-3` ·
`DROPOUT 0.4` · `SEED 777` · 같은 GRU 구조). 다른 것은 하나뿐이다:

| | P3 (58.8028) | P11 멤버 |
|---|---|---|
| epoch | **60, early stopping(patience 10)** | **1~2** |
| LR 스케줄 | ReduceLROnPlateau(patience 3) | CosineAnnealing(T_max=30) |
| val | **64.203** | A0 66.608 |

`epochs=1` 은 P9/P10 의 **CV 최소점**에서 가져온 값이다. 그런데 그 CV 는
`CODE_REPORT §1.5` 가 이미 반증한 계측기다 (2.56 을 0.013 으로 읽었다).
**epoch 선택만 그 계측기를 계속 믿고 있었던 것이다.**

교차 확인: `F3_s777_e1` 의 val 66.996 은 P9 제출본의 val 66.978 과 사실상 같다.
**F3 멤버는 P9 재현이 맞다.** 그렇다면 평균을 끌어내린 쪽은 A0 계열이다.

### 대응 — 제출을 쓰지 않는 진단부터

노트북에 **[진단] epoch 곡선** 셀을 넣었다 (`RUN_EPOCH_PROBE = True`).
A0·F3 를 30 epoch 씩 돌리며 매 epoch val 을 찍는다. **제출 0회, GPU 약 4분.**

```
RUN_EPOCH_PROBE = True
```

곡선이 64 근처로 내려오면 "덜 학습됐다"가 확정이다. 그러면

```python
MEMBER_EPOCHS = (10, 16, 24)     # 최저점 부근 값 2~3개 — 진단 결과대로
MEMBER_CODES  = ("A0", "F3")     # A0 가 끝내 안 내려오면 ("F3",) 로 뺀다
```

로 바꾸고 **멤버 셀부터** 다시 실행한다. (epoch 당 약 2초라 6멤버 × 20 epoch ≈ 4분이다.)

### 왜 이 방향이 여전히 맞나 — 기존 제출본 혼합의 산술

이미 점수가 나온 제출본들의 예측을 실제로 평균해 보면 (오차상관으로 추정):

| 조합 | 예상 Public | 최고 멤버 대비 |
|---|---:|---:|
| P3 + P9 | 57.57 | −1.23 |
| P3 + N1 | 57.28 | −1.52 |
| **P3 + P9 + N1** | **56.72** | **−2.08** |

**앙상블 아이디어 자체는 −2 짜리가 맞다.** 다만 그건 *제대로 학습된* 멤버들끼리의 이야기다.
그리고 서로 다른 노트북의 CSV 를 평균한 파일은 **재현 불가라 제출할 수 없다.**
같은 값을 합법적으로 얻는 길은 하나뿐이다 — **P3 급 멤버와 P9 급 멤버를 한 노트북 안에서
학습해서 평균하는 것.** `A0@최적epoch` + `F3@최적epoch` 이 정확히 그 구성이다.

> 참고: 같은 config·다른 시드만으로는 이득이 거의 없다. P6 의 동일설정 재실행 불일치가
> 4.60 RMS 였고, 그 정도면 K=3 평균의 이득이 0.1 미만이다.
> **이득은 시드가 아니라 config 다양성에서 나온다.**

### 다음 제출 순서 (남은 횟수에 따라)

| 남음 | 순서 |
|---|---|
| 1회 | 진단 → `MEMBER_EPOCHS` 수정 → `S1` 재제출 (기하·물리는 건드리지 않는다) |
